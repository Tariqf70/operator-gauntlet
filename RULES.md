# The rules

Every generated operator is scored against the seven rules below. Each rule is a
deterministic pass/fail check with no LLM judge. A rule can be *stated* (the spec
tells the agent) or *implicit* (an experienced operator author would follow it
anyway). The contract for each spec (`specs/*/contract.json`) records which is
which, and results report the two separately.

Two rules, **R3** and **R6**, are *hidden*. In setup S4 the agent can run the
suite for feedback, but only the five visible rules are shown to it. Comparing
hidden-rule pass rates across setups shows whether feedback taught the agent the
rules or only how to pass the visible tests.

| ID | Rule | How it is checked | Hidden in S4 |
| --- | --- | --- | --- |
| R1 | **Crash-safe, idempotent reconcile.** Killing the manager at any point and restarting it converges to exactly the intended state. | The manager is SIGKILLed at a deterministic crash point: the instant its first create succeeds, before it sees the response (through the harness's API proxy), or for ManagedDatabase the instant the fake cloud stores a create. After a restart the suite asserts exactly one external resource and correct children. | No |
| R2 | **Status discipline.** Status is written through the status subresource, `status.observedGeneration` tracks `metadata.generation`, and conditions don't flap while idle. | CRD has a status subresource; audit log shows status writes on `subresource=status`; after a spec change `observedGeneration == generation`; `lastTransitionTime` of `Ready` is unchanged across an idle window. | No |
| R3 | **Bounded steady-state writes.** A converged operator doesn't write to the API server. | Audit-log writes (create/update/patch/delete) by the manager's user during a 60 s quiet window, compared to the contract's threshold. | **Yes** |
| R4 | **Finalizer lifecycle.** Deletion never hangs and never leaks external resources. | Delete with each deletion policy, and delete while an external create is still in flight. Assert the CR disappears within 30 s and the fake cloud holds exactly what the policy says. | No |
| R5 | **Ownership and garbage collection.** Children carry a controller owner reference, so Kubernetes cleans them up even if the operator is down. | Static check of owner references (envtest). On kind: stop the manager, delete the CR, assert children are garbage-collected. | No |
| R6 | **Conflict handling, no lost updates.** Concurrent writers don't crash the operator, and the operator doesn't erase fields it doesn't own. | A concurrent writer bumps `resourceVersion` on the CR and children at about 5 Hz while spec changes land. Assert the manager never exits, state converges, and the writer's annotations survive. | **Yes** |
| R7 | **Least-privilege RBAC.** The operator asks only for what the contract needs. | Static analysis of `config/rbac/*.yaml`: no `*` in apiGroups, resources or verbs, and no resource outside the contract's allow-list. At runtime the manager runs as a user bound only to that RBAC, and 403s in the audit log are reported. | No |

## Why these rules

Each rule maps to a failure mode that operator authors usually learn about in
production:

- **R1:** duplicate cloud resources after a crash between "create" and "record
  that I created it".
- **R2:** clients and `kubectl wait` can't tell whether status reflects the
  latest spec.
- **R3:** controllers that patch status every loop and slowly fill etcd.
- **R4:** namespaces stuck in `Terminating`, and orphaned cloud bills.
- **R5:** children left behind when the operator is uninstalled or crashing.
- **R6:** hot restarts on 409 conflicts, and operators that fight other
  controllers over labels and annotations.
- **R7:** cluster-admin-shaped roles generated by `+kubebuilder:rbac` markers
  with wildcards.
